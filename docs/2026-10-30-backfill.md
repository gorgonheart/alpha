# 首次启动「空档补算」（core/backfill.py）

2026-10-30 新增。解决采集端重启后除 init 那一分钟外、其余 offset 无数据可用的空转问题；同日追加三道数据正确性守卫。

## 1. 问题

`init_dirs()` 每次重启都会删除 resample 与 preprocess 目录。重启后：

- `init_history()` 只调 `resample_history()`，为**所有 offset** 写同一个 `run_time` 的 resample ready；
- `preprocess_offset_data()` 只在 `run_time.minute` 命中 `enabled_hour_offsets` 的正常轮里跑。

所以除 init 那个分钟归属的 offset 外，其余 offset 的 `preprocess_1h_resample/<offset>/` 是空的，消费者读不到任何东西，只能干等自己那一分钟。以 `enabled_hour_offsets=('20m','40m','55m')`、08:00 启动为例，40m 要等到 08:40，也就是近 40 分钟空转。

## 2. 做法

`update_all()` 进入「不在 Offset 中，休息 60s 后跳过」之前调用 `maybe_backfill(handle)`：

```
maybe_backfill            # 主进程：glob 检查 + 冷却 + 时间预算，最多取前 2 个缺 ready 的 offset
└─ ProcessPoolExecutor(1)
   └─ run_backfill        # 子进程：逐个 offset 校验并补算
      └─ backfill_one_offset
         0. 基础数据新鲜度校验（不满足直接返回 stale，什么都不写）
         1. update_binance_meta      # exginfo_<run_time> + 实时资金费（联网，几秒）
         2. update_symbol_match      # spot_swap_matches_<run_time>
         3. local_resample_offset     # 读磁盘 5m 全量，本地重采样出该 offset 的 ready
         4. preprocess_offset_data    # 出 batch / pivot / arrow + spot_dict / swap_dict ready
```

约定的三件事（2026-10-30 与用户确认）：

| 项 | 取值 | 说明 |
|---|---|---|
| 补算范围 | 按 `enabled_hour_offsets` 顺序，取前 2 个缺 ready 的 | 已 ready 的跳过，只缺一个就补一个 |
| run_time | 该 offset **最近一个已到达**的边界 | 07:53、offset=20m → 07:20；不提前伪造未来的 ready |
| 联网 | 允许少量 | preprocess 强依赖 `exginfo_<run_time>` 与 `spot_swap_matches_<run_time>`，不写必失败；不重新拉 K 线 |

## 3. 与「到点更新」的代码一致性

计算口径**完全共用同一份函数**，不是另写一套：

| 步骤 | 到点更新 | 补算 |
|---|---|---|
| exchangeInfo + 资金费 | `update_binance_meta` | 同 |
| 现货/永续映射 | `update_symbol_match` | 同 |
| 重采样聚合 | `calc_resample` | 同 |
| 合并/去重/缺口/截断 | `update_resample_candle` | 同 |
| 预处理出 ready | `preprocess_offset_data` | 同 |
| 读 K 线数据源判定 | `read_candle_data`（binance 优先、data_api 兜底） | 同 |

`theoretical_start = run_time - kline_count_1h * resample_delta`、`num_candles`、`resample_interval`、`offset_str` 四个入参也一致。

**唯一实质差异是重采样的输入窗口**：

- 到点更新：API 现拉 `once_update_candles = 99` 根 5m（≈8.25 小时），与磁盘历史 concat 后 `tail(num_candles)`，是增量拼接；
- 补算：读磁盘 5m 全量、按 `< run_time` 过滤后整体重算。

两者产出的尾部队列等价，补算少一次累积误差。另有两处非实质差异：

- 到点更新在 `resample_mgr.has_symbol(symbol)` 时会丢弃 API 窗口首根（`binance_update.py:98-99`，首根可能被 API 截断而不完整）；补算**不丢**，因为全量重算的首根由 `theoretical_start` 保证完整，丢了反而少一根。
- 补算不写基础 5m（磁盘本来就有），也不做 `sleep_until_run_time`。

## 4. 三道守卫（同日追加）

前两版实现只保证「能算完」，实测发现三处会静默产出错误数据，因此加入守卫。

### 4.1 未来数据截断（最关键）

`resample_history()` 为所有 offset 写同一个 `run_time`。实测现场：init 在 07:40 跑完后，`binance_swap_1h_resample/{20m,40m,55m}` 各有 1512 个文件、ready 全是 **07:40**，其中含 07:20 之后的 K 线。

补算目标若是 07:20，`update_resample_candle` 会把这份更晚的 df_old 一起 concat、再去重 `tail`，**未来 K 线会留在文件里**，preprocess 再把它变成 pivot/arrow → 未来函数。

`_truncate_resample_before()`：合并前若 df_old 有 `>= run_time` 的行，先 `save_data_file` 截断到 `< run_time`，再走原来那套 `update_resample_candle`。仅截断旧数据，不改变共用代码路径。

### 4.2 基础数据新鲜度

基础 5m **只在 offset 轮次更新**，且在 `run_time + 2 分钟` 才落盘（`update_base_candles` 里有 `sleep_until_run_time(run_time + 2min)`）。上一轮失败或刚 init 完时，磁盘可能还缺最后 1~2 根；此时照样写 ready，产出的 K 线会**静默偏短且不报错**。

`newest_base_time()` 只读最后一个分区（探针 BTCUSDT / ETHUSDT / SOLUSDT / BTCUSDC，实测约 10ms，与交易对数量无关）；`is_base_data_fresh()` 要求 `最新根 + base_interval >= run_time`，不满足则返回 `stale`，**不写任何文件**。

### 4.3 offset 往返校验

要求 `get_offset_from_runtime(run_time, resample_interval) == offset`。不一致说明 `enabled_hour_offsets` 与 `resample_interval` 配置不匹配，此时 resample 会写进错误的 offset 目录，直接 `skip` 并提示。

### 4.4 失败语义

`run_backfill()` 返回 `{offset: ok | stale | skip | error}`：

| 状态 | 含义 | 冷却 |
|---|---|---|
| `ok` | 补算完成 | — |
| `stale` | 磁盘基础数据还没覆盖到 run_time | **清除冷却**，下个空档（约 60s）重试 |
| `skip` | 时间预算不足 / 配置不一致 | **清除冷却**，下个空档重试 |
| `error` | 抛异常 | 30 分钟冷却，避免反复打重活 |

时间预算：距下一个 offset 不足 `MIN_REMAIN_SECONDS = 240` 秒不开工，避免补算拖过正常轮次。

## 5. 验证

离线（不启动业务、不写业务目录）：

- `newest_base_time`：spot/swap 均为 `07:50`，探测 11ms / 8ms；
- 目标 07:20 / 07:40 / 07:55 全部 `fresh`，offset 反推一致；`now-0/5/10/15min` 全部 `stale`（正确拦截）；
- `backfill_one_offset(run_time=now)` 返回 `stale`，resample 目录文件数 1512 → 1512 未变（确认未写盘）；
- `run_backfill(['7m'])` → `skip`；
- 临时目录 + 真实基准数据模拟「init 已写 07:40 → 补算 07:20」，3 个 symbol 产物最大 `candle_begin_time` 均 < run_time（末根 06:20，正好是 offset 20m 的对齐边界），`check_ready(run_time)` 为 True。

## 6. 已知边界

- **补算只遍历 `base_candle_dir` 里的 symbol**。init 之后才上市、还没写过基础数据的合约不在其中，该 offset 首轮会缺它；等它自己那一分钟走正常路径时，会作为新 symbol 补进 `old_market_dict`（`preprocess.py:326-330`），无需额外处理。
- **补算写出的 ready 是过去的边界**（07:20），消费者的 `check_bmac_update_flag` 按自己的 run_time 找 `spot_dict_<ts>.ready`，所以补算**不会**让消费者提前拿到数据。收益在别处：到 08:20 时 `gen_batch_data_incremental` 发现 batch pkl 已存在，只追加新行，不再全量算。
- **`data_api` 分支**：补算只用 binance 本地重采样。若 `use_api['kline']=True` 且 binance resample 缺失，正常轮会回退 data_api，补算不会——`read_candle_data` 仍是 binance 优先，故仅影响该回退场景。
- 补算重启后第一个「剩余时间 ≥ 240 秒」的空档才开始，若重启恰好临近 offset（如 07:53 启动、08:00 是 offset），要等下一轮。
